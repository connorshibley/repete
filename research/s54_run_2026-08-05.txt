CORRECTIONS TO THE FROZEN SPEC

  The spec cannot be edited — a verdict exists, and `register_gate.py` refuses
  re-registration at that point, which is the apparatus working as designed.
  So the errors are recorded here instead. §41's precedent: superseded text
  gets a note, not an edit.

  FAILURE MODE 4 IS WRONG. It says:

    "`correlation` and `heat` live in `pre_trade_checks`, which the simulator
     never calls (pinned by tests/test_rail_interactions.py), so this run says
     nothing about it. A clean census here does not cover it."

  The premise is right and the conclusion does not follow. Those rails do raise
  inside `pre_trade_checks`, and the simulator does not call that function —
  but `simulate_ensemble` REIMPLEMENTS the same three call sites inline
  (`backtest.py:1026` heat, `:1039` correlation, `:937` daily_cap), routed
  through the same `risk.*` helpers. So the census DOES measure the correlation
  cap, and it shows the same direction-blind displacement the sector cap does,
  smaller: 72 / 77 -> 90 in s54c.

  The error was mine, made while reading `test_rail_interactions.py`'s rail
  census as if it enumerated which rails RUN rather than which rails RAISE
  inside each function. It was frozen into the spec before the run, which is
  the correct order — and being frozen is why it can be caught here rather
  than quietly forgotten.

  Worth noting for its own sake: two call sites for one rail is exactly the
  hazard `sector_open_count`'s docstring names — "`strategy_slots` is the
  cautionary precedent: its count is derived in two places … and re-derived
  counters are the shape behind §13's missing rails". Here the arithmetic is
  shared (both sides call `risk.correlated_position_count` with thresholds from
  the same config), so this is a structural risk rather than a live divergence
  and no register entry is owed. It is written down so the next person does not
  have to rediscover which functions the simulator does and does not call.
